Meta-Engineering: Why AI Agents Turned Me Into a Manager

TS
Thomas Saulou
Jun 5, 2026 · 9 min read

I asked an AI agent to render a Photoshop file in a browser.

It wrote 400 lines of React in 30 seconds. Clean components, proper TypeScript, reasonable structure. I was impressed for about two seconds — until I opened the browser. The text didn't wrap. A headline that should have been two lines bled off the right edge of its container in a single, infinite line. The layers were stacked backwards: the background image was on top, covering everything else. And the entire composition was invisible, because every layer had its opacity set to zero.

I described what was wrong. The agent tried again. Still wrong — different wrong. The text now wrapped but at the wrong width. The layers were no longer inverted but the artboard wasn't clipping. I described it more carefully. Wrong a third time. Then a fourth.

After the tenth iteration, I realized the problem wasn't the agent.

The problem was me.

I was doing what a bad manager does — giving vague verbal feedback and hoping for perfect output. "The text should wrap." "The layers are in the wrong order." "The opacity looks off." These are the engineering equivalent of "make it pop" in a design review. They're technically accurate and practically useless.

So I did what a good manager would do. I stopped trying to describe the problem. I built a system that makes the feedback precise, automatic, and self-correcting.

I never described a rendering bug in words again.

Something shifted, and I didn't have a word for it

Here's what happened next. Instead of fixing the UI myself — instead of writing the CSS that makes text wrap, adjusting the z-index, correcting the opacity — I built a tool. A tool that:

  • Extracts the composite image Photoshop embeds in every PSD file (its own rendering of the design)
  • Launches a headless browser and screenshots what our code actually renders
  • Compares the two images using perceptual similarity scoring
  • Checks every layer structurally: are the bounds right? The font? The opacity? The stacking order?
  • Returns a structured JSON report with a score, a list of issues, and — crucially — an exact fix for each one

The output looks like this:

{
  "score": 72,
  "pass": false,
  "issues": [
    {
      "id": "TEXT_BOX_OVERFLOW",
      "layer": "Transforming Employee Journeys",
      "severity": "high",
      "expected": "text wraps at 580px (2 lines)",
      "actual": "single line, 720px wide",
      "fix": "Change textFrameType: textInfo.pointPlaced === true ? 'point' : 'box'"
    },
    {
      "id": "Z_ORDER_INVERSION",
      "layer": "Background Image",
      "severity": "critical",
      "expected": "z-index 0 (bottom)",
      "actual": "z-index 12 (top)",
      "fix": "Use incrementing z-counter: z++ not z--"
    }
  ]
}

When I pointed the agent at this tool instead of explaining problems in English, something remarkable happened. The agent ran the check, read the JSON, applied the suggested fixes, re-ran the check, and scored 94 on the second attempt. Two iterations. Self-guided. No human feedback needed.

I stopped being a developer. I started being something else. I didn't have a word for it yet.

I'm calling it meta-engineering

Traditional engineering means you write the code that solves the problem. Meta-engineering means you build the system that enables someone — or something — else to solve the problem repeatedly, autonomously, and correctly.

This isn't a new concept. It's an accelerating one.

Compilers were meta-engineering. At some point, developers stopped writing machine code and started building tools that translate human-readable languages into machine instructions. The work moved up a level of abstraction: you didn't solve the problem directly, you built the system that solves it.

CI/CD was meta-engineering. You stopped running tests manually and built pipelines that run them on every commit. DevOps was meta-engineering. You stopped hand-deploying to servers and wrote infrastructure as code. Each time, the developer moved further from the direct work and closer to the system that ensures the work happens correctly.

AI agent tooling is the next layer. You stop implementing features. You build the feedback loops, validation harnesses, and knowledge bases that agents consume.

I see three pillars to this kind of work.

The first is feedback loops. An agent can't fix what it can't see. My PSD rendering agent had no way to compare its output against Photoshop's. It was coding blind. The moment I gave it "eyes" — a visual diff tool that outputs a score and a heatmap — it could self-correct. Feedback loops are the eyes, ears, and nervous system of an autonomous agent.

The second is knowledge codification. Every senior developer carries around a mental catalog of "things that always go wrong." Text never wraps correctly when the frame type is ambiguous. Layer order is always inverted the first time you parse a PSD. Opacity from ag-psd is a 0-to-1 float, not 0-to-255. This knowledge lives in people's heads. Meta-engineering means writing it down — not as documentation, but as machine-readable detection rules paired with fix suggestions. I built a knowledge base of 21 known PSD-to-CSS pitfalls. Each one has a detection function, an explanation, and an exact code fix. The agent doesn't need to "learn" these patterns. It just queries the catalog.

The third is guardrails. Before the agent writes a single line, you define what "correct" looks like. Type systems. Tolerance profiles. Scoring thresholds. In my case, I defined three profiles: strict (pixel-perfect for component libraries), standard (production pages), and dev (work-in-progress). Each specifies acceptable SSIM scores, maximum structural failures, and per-layer-type tolerances. Text layers get looser thresholds than image layers because browser font rasterizers will never match Photoshop's exactly. These definitions exist before any code is written. They are the specification — not in a document, but in code.

Wait — this is just management

Here's the part that made me uncomfortable.

What I just described — defining success criteria, building evaluation systems, providing structured feedback, letting someone else do the implementation, and trusting the loop — is not engineering.

It's management.

Think about what a good engineering manager does. They don't write the code. They define what "done" looks like. They create feedback mechanisms: one-on-ones, code reviews, dashboards, sprint retrospectives. They codify team knowledge into playbooks and runbooks. They set guardrails: coding standards, architecture decisions, review checklists. And then they let the team execute.

Now think about what I did with the PSD fidelity tool. I didn't write the rendering code. I defined what "correct" looks like (tolerance profiles, scoring thresholds). I created feedback mechanisms (visual diff, structural assertions, a 0-to-100 score). I codified knowledge (a pattern catalog of 21 known failure modes with detection rules and fix suggestions). I set guardrails (type systems, schemas, per-layer tolerances). And then I let the agent execute.

The parallels are exact. Uncomfortably exact.

This doesn't mean developers are becoming people managers. Nobody is scheduling one-on-ones with Claude. But the intellectual work — the core question of "how do I make sure the output is right without doing it myself" — is identical.

A junior developer asks: how do I build this?

A senior developer asks: how do I make sure this is built correctly?

A meta-engineer asks: how do I build the system that ensures everything is built correctly, forever, without me?

That last question is what engineering directors have been asking for decades. Developers are just now arriving at it — not because they got promoted, but because their "team" can now run code.

What a meta-engineer's week looks like

In 2023, my week was: write code, write tests, review PRs, debug, write more code.

In 2026, my week is different. I design types and schemas. I build validation tools. I write knowledge bases. I configure tolerance profiles and scoring thresholds. I define what "correct" means for each type of output. Then I hand the implementation to an agent. The agent writes the code, runs my validation tools, reads the structured feedback, iterates, and converges on a passing result. I review the final output.

Three patterns have emerged in this workflow.

Eval-driven development. Write the eval before the feature. Define what "correct" looks like as a machine-checkable assertion — not a test of implementation details, but a validation of the output's properties. Then let the agent iterate until it passes. This is TDD, but one level of abstraction higher. You're not testing functions. You're testing the system's output against a ground truth.

Knowledge bases as code. Stop writing comments that explain what goes wrong. Start writing detection rules that catch what goes wrong. "When a text layer's pointPlaced field is undefined, ag-psd defaults it ambiguously. The rendering will fail to wrap. Detection: text content wider than bounding box by more than 15%. Fix: default to box when pointPlaced is not explicitly true." This is not documentation. It is an executable rule that agents consume directly, with no human interpretation required.

Tool-calling over prompting. I used to write 500-word prompts explaining how to validate a PSD rendering. Now I expose an MCP tool called check_fidelity that takes a PSD path and a URL, runs the full comparison pipeline, and returns structured JSON. The agent calls the tool and reads the result. Agents are dramatically better at processing structured data than interpreting natural language instructions. Give them tools, not prose.

The question I keep coming back to

I used to measure my productivity in lines of code written. Now I measure it in agent iterations eliminated. The best day I had last month, I wrote zero product code and deployed three features — because I had already built the systems that let the agents ship them correctly.

The role I'm describing — designing feedback loops, codifying quality, building the tools that build the product — doesn't have a job title yet. "Meta-engineer" is my attempt. You might call it something else.

But here's the question I keep coming back to: if the highest-leverage thing a developer can do is no longer writing code, but designing the systems that make code correct — then what exactly separates us from the best engineering managers we've ever worked with?

Maybe nothing.

Maybe that's the point.
